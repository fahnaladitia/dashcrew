## 0.8.0

Launch-ready: Go is a built-in platform, Flutter gets drift, chopper and amplitude packs, `dashcrew guard init` tries the guard in ten seconds, the agent can commit and push behind a prompt the guard enforces (`ask`), `install.sh` installs a release, and the guard no longer lets an unknown tool through in silence. Run `dashcrew sync` and commit what it writes: every project with Claude Code gets one changed line in `.claude/settings.json` (the hook passes `claude-code`), a Flutter project gets a changed verify skill (a read-only `dart format` check) and, with `policy.formatter: false`, a reworded formatter line in AGENTS.md, a project on `platform: other` or a project platform gets a reworded testing line in AGENTS.md, and `.ai/lock.json` changes. `guard_min_version` rises to 0.8.0 only in a project that sets `agent_commit: ask`; there, every teammate installs 0.8.0 before that sync is committed. 0.7.0 was published as a release candidate only (`v0.7.0-rc.1`); its changes, below, ship in 0.8.0.

- Changed: Go is a built-in platform. `init` on a Go module picks `platform: go` like it picks Flutter, writes only `.ai/project.yaml`, and proposes the `http` and `db` packs from the modules `go.mod` requires (and a `sqlc.yaml`), printed as evidence. The Go rules and backend guard rules now come with each dashcrew release instead of being copied once. A project with `.ai/platforms/go/` from the starter keeps it and its output; deleting an unedited one moves it to the built-in platform (see `docs/troubleshooting.md`).
- Changed: `dashcrew platform new <name>` ejects any built-in platform (`flutter`, `go`) into `.ai/platforms/<name>/` for a team that wants to own its rules; the copy's `platform.yaml` names the dashcrew version it came from. `--http` and `--db` are for `go` only.
- New `policy.agent_commit: ask` and `policy.agent_push: ask`: the agent runs the commit and the push of its task branch, and the guard makes the agent ask you to approve each call, instead of the question being an instruction only. Claude Code shows its permission prompt and Antigravity a `force_ask` prompt, also for `bash -c "git commit"` and the other forms the guard unwraps. Codex hooks cannot ask for approval, so Codex calls are blocked there, and so are calls from Cursor running the Claude Code hook, whose handling of an ask answer is undocumented. A project with `ask` needs dashcrew 0.8.0 on every machine (`guard_min_version`).
- Changed: the Claude Code hook command passes `claude-code` after the policy, so the guard knows which agent called. Every project with Claude Code gets this one-line change in `.claude/settings.json` on its next `dashcrew sync`; until then `doctor` and `check` report the hook as different from what sync writes. Older guards ignore the argument.
- New `dashcrew guard init`: the guard alone, without `.ai/project.yaml`. It writes the default policy (git commit, push and history rewrites blocked, formatters blocked), `.ai/bin/guard` and the hook of each agent in `--agents` (Claude Code by default), keeping the user's own hook entries, then runs the guard checks of `doctor`. A later `init` and `sync` take the files over without `--force`, and `doctor` in a guard-only project runs only the guard checks.
- Docs: the README is a one-screen introduction (what the guard blocks, why a team picks dashcrew, a quickstart, a comparison with rulesync and Ruler). The reference moved to `docs/`: `profile.md`, `commands.md`, `guard.md`, `team.md`, `knowledge.md`, `release-lines.md` and `troubleshooting.md`, with `architecture.md` new for contributors. New `docs/recipes.md` holds four complete profiles to start from: a Flutter app with bloc, get_it, go_router and two flavors, a Python service on `platform: other`, a team on three agents with the GitHub merge gate and `agent_commit: ask`, and a Go service.
- Changed: `init` has no dead end any more. A Go module gets the built-in `go` platform (above) instead of exiting 1 with a tip. Under `platform: other` it prints the root files that identify a stack before the prompts and proposes them as `detect`. A required answer left empty is asked once more, then `init` stops instead of asking until input ends.
- Changed: `doctor` `skills` no longer warns about an outside skill the generated files use only when installed (`idea-refine` and the like): it is a note on an ok check, so a fresh project has no warning. A skill named in the AGENTS.md project block that is not installed still warns.
- Fixed: messages that read wrong. A path named with `-p .` (the default) is printed clean, not as `<folder>/.`, which read `<folder>/..` before a full stop. `doctor` and `check` widen the ID column to keep long IDs (`antigravity-hook`, `codex-skills-budget`) apart from their detail. An MCP check with no server to define says so instead of `defined:` and nothing. On `platform: other` and project platforms, AGENTS.md says to run the analyze command on the changed paths instead of appending `<changed paths>` to it (`ruff check . <changed paths>`): run `dashcrew sync` and commit what it writes.
- New `install.sh`: `curl -fsSL https://raw.githubusercontent.com/fahnaladitia/dashcrew/main/install.sh | sh` installs the latest release (or `DASHCREW_VERSION`) into `~/.local/bin` (or `DASHCREW_INSTALL_DIR`) on macOS and Linux, without `sudo`. It refuses an archive whose SHA-256 is not in the release's `checksums.txt`, or whose binary reports another version. CI installs each commit's own build through it from a local folder, so the download counts of a release are people's installs, and installs the published release through it, `brew` and `go install` daily. When the install folder is not on `PATH`, it says how to add it: an `export PATH` line, or `fish_add_path <dir>` when `$SHELL` is fish.
- Changed: a tool name the guard does not know is no longer let through in silence. When its input holds a `command` (under `tool_input`, at the top level, or as Antigravity's `CommandLine`), the command is checked as a shell command, so a renamed shell tool still has `git push` blocked. Every unknown tool is logged, and `doctor` `guard-log` reports it, naming the tool when the name is a plain identifier. The hook matchers dashcrew writes never send such a tool, so a line in the log means an agent changed its tools or another agent runs the hook.
- Fixed: `doctor` `guard-binary` accepts a release candidate of the minimum version, as the shim does: `0.8.0-rc.1` no longer warns as older than `0.8.0`.
- Fixed: the guard reads Cursor's shell input, the `Shell` tool of `preToolUse` and the `command` of `beforeShellExecution`, and blocks what it blocks for Claude Code's `Bash`. Cursor runs the Claude Code hooks in `.claude/settings.json` by default; if it sends its own input there, a `claude-code` project opened in Cursor had every shell command let through, `git push` included. Writes and deletes from Cursor are not read yet. `guard-log` names Cursor as `cursor`.
- New `storage: drift` pack for Flutter: one database class opened once, generated code never edited, versioned `onUpgrade` steps, `variables` for raw SQL, awaited queries in a transaction, and in-memory database tests. `init` proposes it for `drift` instead of `{use: other, name: drift}`; a profile that already says `use: other` keeps the generic rules until it switches (#56).
- New `network: chopper` pack for Flutter: generated services in `client_dir`, one configured `ChopperClient`, bodies decoded by its converter, a non-2xx `Response` mapped to app errors in repositories, and `MockClient` tests. `init` proposes it for `chopper` instead of `{use: other, name: chopper}` (#57).
- New `analytics: amplitude` pack for Flutter, like `mixpanel`: ask before tracking, the SDK only behind the facade, constants for names, and a `server_zone` param. The guard blocks importing `package:amplitude_flutter` in `lib/` outside local packages. `init` detects `amplitude_flutter` (#58).
- Changed: Flutter verify runs `dart format --output=none --set-exit-if-changed` on the changed Dart files in phase 1, so a branch that fails a CI format check no longer reports ready. With `policy.formatter: false` the agent fixes what it lists by hand. The guard now allows a `dart format` that cannot write (its last `--output` is `none`, `show` or `json`, with no option it does not know) under any policy; `dart fix` and other `dart format` calls stay blocked. Every Flutter project gets a changed verify skill and a reworded formatter line in AGENTS.md: run `dashcrew sync` and commit what it writes. An older dashcrew's guard blocks the check, and verify says to report that (#67).

## 0.7.0

Trust: an interrupted sync finishes with a plain `dashcrew sync`, CI catches a lost guard hook, the guard logs every call it lets through unchecked, and new policies let the agent commit and push on your answer. Run `dashcrew sync` and commit what it writes: usually only `.ai/lock.json`, plus new AGENTS.md text in a project with `policy.agent_commit: true`. `guard_min_version` rises to 0.7.0 only in a project that turns on `policy.agent_push`, so every member installs 0.7.0 before that sync is committed.

- New `policy.agent_push` (needs `agent_commit: true`): at the end of each task the agent asks whether to commit and push the task branch for you or leave both to you, and acts only on your answer. The guard then allows a push that names a branch, and still blocks a force push, a deleted remote branch, `--all`, `--mirror`, `--tags`, a push to a `project.base_branches` branch, and a push that names no branch. A project that turns it on needs dashcrew 0.7.0 or newer on every machine: the shim refuses an older one, whose guard would allow every push.
- Changed: with `policy.agent_commit: true` the agent no longer waits to be asked to commit; at the end of each task it asks whether to commit for you or leave it to you, and prints the commit command when you keep it. Projects with `agent_commit: true` get new text in AGENTS.md: run `dashcrew sync` and commit what it writes. The default (`agent_commit: false`) is unchanged.
- Changed: `sync` and `me sync` write each file through a temporary file and a rename, so an interrupted run leaves a file's old content or its new one, never part of it. A file that already holds what `sync` renders is no longer a conflict, whatever the lock says, so a plain `dashcrew sync` finishes a sync that stopped before writing `.ai/lock.json` instead of asking for `--force`; a hand-edited file still stops it. An MCP server that already matches dashcrew's definition in `.mcp.json` or `.agents/mcp_config.json` becomes dashcrew's, and is removed when the catalog drops it. A linked `~/.codex/AGENTS.md` or other personal instruction file stays a link: its target is rewritten.
- Changed: `dashcrew check` also runs the guard hook check of each agent in the profile (`hook`, `codex-hook`, `antigravity-hook`, from the committed files), so a pull request that loses the guard hook to a hand edit of `.claude/settings.json` or a merge fails the gate.
- Changed: the guard logs a policy it was given but could not use (missing, not a file, unreadable, not JSON, invalid, or failing while it is applied) in the same log as malformed payloads, so `doctor` `guard-log` reports it. It still lets the call through. `guard-log` now reads "let N tool calls through unchecked".
- Fixed: `worktree create`, `worktree link`, `link` and `me sync` no longer rewrite the git exclude file when they cannot read it; they stop with the read error, so the lines already there are kept. Outside a git repository they name the failing `git rev-parse` instead of `open : no such file or directory`.
- Fixed: `worktree create` starts the branch from the commit it resolved for `<base>`, and stops when the new worktree is not on that commit (moved by a `post-checkout` hook, for example), naming both commits, instead of reporting `branch: <branch> (base <base>)` for a branch that carries other commits (#30).
- Changed: a release candidate tag (`v0.7.0-rc.1`) is published as a GitHub pre-release and is not pushed to the Homebrew tap; `brew upgrade` installs final releases only. Try a candidate with `go install github.com/fahnaladitia/dashcrew/cmd/dashcrew@<tag>`.

## 0.5.0

Readable chat blocks, skills a team can adopt and each member can switch on, and a guard that runs under Antigravity. A project's generated files change: run `dashcrew sync` and commit what it writes. In a project with the antigravity agent the shim then accepts dashcrew 0.5.0 or newer only, so every member installs 0.5.0 before that sync is committed.

- Readable chat blocks (#18): step 0, review, verify, learn, build-fix and the end-of-task summary print as plain-text blocks with one layout: a title line, a 72-column `=` rule, `Label  value` rows, then each list under its own `-- Name ---` rule, columns aligned with spaces so every value copies clean. A comparison is a table in that layout. Step 0 numbers its assumptions and questions (`A1`, `Q1`), lists skills, criteria and branches as rows, and ends with the reply it expects; with a question tool the agent asks through it. The review verdict comes first. The full step 0 template moves from AGENTS.md to the `prompt-polish` skill, and the `SUMMARY` template to `pr-description`, where tracker and analytics packs add their rows. The main session always asks an open question, with the agent's question tool when it has one, and waits.
- One source per chat block (#21): a platform overrides the prose around a block, never the block, so a layout change is made in one file; the `reviewer` role names the `code-review` verdict format instead of copying it, and the verify QA line reads the same on every platform.
- Project skills (#20): a skill the team adopts lives in `.ai/skills/<name>/` (`SKILL.md`, copied as written, never rendered, and `meta.yaml` with `description`, `when_to_use`, `review`, `optional`). A required one is written for every agent and joins the skill index. An optional one is written by `dashcrew me sync` only into the clone of a member who lists it in `.ai/me.yaml` `skills`, git-excluded, so no agent of another member can pick it; a `review` skill cannot be optional. A member tries a skill first in `~/.dashcrew/skills/<name>/` with `skills` in `~/.dashcrew/me.yaml`, linked for Claude Code. New `dashcrew skill adopt <name | folder> [--required]` copies it into the project.
- Supporting files (#22): a project skill's other files (`references/`, `scripts/`, templates) are written next to each agent's `SKILL.md`, with the source's executable bit; `me sync` tracks the files it writes for an optional skill in `.dashcrew-me` and removes only those.
- Skill limits warn (#23): a symlink, a pipe or device, a file over 1 MiB, or a file past the first 50 in a skill folder is left out with a `sync` and `doctor` warning instead of stopping every command; a symlinked `SKILL.md` or `meta.yaml` is still refused. `me sync` reads `.ai/skills` alone, so a broken project pack no longer blocks a member's optional skills.
- Antigravity guard (#25): agy runs a hook in the folder of its `hooks.json`, so `./.ai/bin/guard` in `.agents/hooks.json` was not found and the guard often did not run. The hook now finds the shim from `.agents/`, the workspace root, a project below the git toplevel or a checkout without git, and passes the policy. The guard answers every Antigravity call with a decision (`allow` hands the call on; agy fails closed without one) and also checks agy's other write tools (`create_file`, `edit_file`, `str_replace_editor` and more). `doctor` asks `agy -p /hooks` whether the guard is active and says to trust the folder when it is not. A project with the antigravity agent needs dashcrew 0.5.0 or newer: run `dashcrew sync` to rewrite `.agents/hooks.json` and the shim.
- The guard corpus record keeps its line order when the goldens are rewritten (#19).

- Multi-repo work, for any layout and any way an app consumes a dependency. `project.links` lists the dependencies a task may point at a local checkout. `dashcrew link add/ls/remove` writes the platform's link file (`pubspec_overrides.yaml`, or `go.work` through `platform_config.link`) after checking the package name, and excludes it from git; `doctor` reports a link file git would commit, a committed one, missing checkouts, and linked checkouts on another branch (info).

- Tracker: a `github` tracker pack for GitHub Issues, with status in a Projects field (`mode: project`) or in labels (`mode: labels`), PRs linked with `Refs #<n>` by default. With any tracker, the `branching` and `pr-create` skills carry the status flow as explicit steps; AGENTS.md is unchanged.

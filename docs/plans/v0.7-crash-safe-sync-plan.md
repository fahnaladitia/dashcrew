# v0.7: crash-safe sync

Tier: standard (`projectfiles`, `sync`, `adapters` and `me`; behavior change in sync's conflict rule). No generated output changes, so no golden is rewritten.

First item of the v0.7.0 "Trust" milestone in `docs/ROADMAP.md`.

## Problem

`dashcrew sync` writes the generated files one by one, removes stale ones, merges adapter config, and writes `.ai/lock.json` last (`internal/sync/sync.go:220-336`). Any write is in place (`os.WriteFile` in `internal/projectfiles/projectfiles.go:81`).

When a sync stops partway (Ctrl-C, a crash, a full disk, a killed CI job), two things can go wrong:

1. **A truncated file.** `os.WriteFile` truncates first, so a stop during the write leaves a file that is neither the old nor the new content.
2. **New files, old lock.** Every file written before the stop holds the new content while the lock still has the old hash. The conflict rule (`sync.go:200-212`) treats a locked file whose hash differs as edited by hand, even when its content is exactly what this sync is about to write. The next sync fails with "Files changed outside dashcrew (rerun with --force to overwrite)", and `--force` also overwrites real hand edits in other files.

`me sync` has the same in-place writes on the user's global instruction files and registry (`internal/me/sync.go:118,726,747`), where a truncated file affects every repository on the machine.

## Changes

### 1. Atomic writes in `projectfiles`

`Project.WriteIfChanged` writes to a temp file in the target's folder (`.<name>.dashcrew-*`), syncs it, sets the mode, then renames it over the target. If anything fails, it removes the temp file.

- **Mode.** An existing file keeps its permission bits. Today `os.WriteFile` keeps them because it does not re-create the file, so the rename must copy them, or skill scripts and the guard shim would lose their execute bit between the write and `filemode.SetExecutable`. A new file gets `0o644`, as now.
- **Links.** Unchanged: a link on the way is still removed first (`LinkWithin`), so the rename never lands in a link's target.
- **Windows.** `os.Rename` replaces an existing file on Windows (`MoveFileEx` with `MOVEFILE_REPLACE_EXISTING`). It fails if another process holds the target open; the error is returned as today.
- **Exported helper.** `projectfiles.WriteAtomic(path, data, mode)`. The adapters' `writeJSON` and every other `os.WriteFile` in sync's path go through it.

### 2. A file that already holds the generated content is not a conflict

In `RunWith`'s conflict loop, a locked file whose content equals the content this sync renders is not a conflict, whatever its locked hash. That is already the rule for unlocked files (`TestAnUnlockedFileThatDiffersIsAConflictButAMatchingOneIsNot`); this extends it to locked ones.

Effect: after an interrupted sync, the next plain `dashcrew sync` finishes the job without `--force`. Files the stopped run did not reach still match the old lock and are rewritten as usual. Truncated files can no longer happen because of change 1.

The rule does not hide hand edits: a hand-edited file differs from the rendered content, so it is still a conflict.

### 3. `me sync` uses the same helper

The three writes at `internal/me/sync.go:118,726,747` and the skill copies at `:780,817,820` go through `projectfiles.WriteAtomic`.

### 4. MCP servers written by an interrupted sync stay owned

`MergeJSONMcpServers` (`internal/adapters/adapter.go:239-258`) takes ownership of a server only if it is new or already owned. After an interrupted sync, `.mcp.json` holds dashcrew's server but the old lock does not list it as owned. The next sync then leaves it unowned, and a later catalog change will not remove it.

Proposed rule: a server whose current definition equals dashcrew's is owned. See question 2.

## Not in this plan

- **An inter-process lock for `sync`.** Nothing runs sync automatically: `worktree watch` and the generated hooks do not call it. Two concurrent syncs therefore need two people or two terminals on one checkout, and a lock file brings its own stale-lock problem after a crash, which is exactly what this plan removes. The roadmap item is dropped unless someone hits it.
- **A `lock.json.next` journal.** Change 2 makes the old lock plus the rendered output enough to recover, so a journal adds a second recovery path without a case it alone fixes.
- **Other in-place writers** (`spec`, `knowledge`, `ledger`, `link`, `worktree` exclude, `initproject`). They write one file each per command, so an interruption costs one file. They move to `WriteAtomic` in a later small task.

## Decisions (maintainer, 2026-11-17)

1. A file edited by hand and then back to exactly the rendered content is not a conflict: agreed.

## Result

- `projectfiles.WriteAtomic`: temp file beside the target, write, `fsync`, chmod, rename; the temp file is removed on any failure. It follows a link at the path and replaces the link's target, so a `~/.codex/AGENTS.md` linked to a dotfiles repo stays a link (it did with `os.WriteFile`; a plain rename would have replaced the link).
- `WriteIfChanged`, and through it the adapters' `writeJSON` and the Codex block, use it. So do the six writes in `internal/me/sync.go`.
- `sync.go` conflict loop: `alreadyRendered` (a generated file whose content equals the rendered content) is never a conflict.
- `MergeJSONMcpServers`: an exact match becomes owned.
- Tests: 4 in `projectfiles`, 2 in `sync` (stopped sync finishes; a hand edit still blocks), 1 in `adapters`, 1 in `me` (linked Codex file). The `me` test passed before the change too: it pins the link behavior the rename would otherwise break.
- Goldens: no change in `test/golden`, `cmd/dashcrew/testdata` or `internal/guard/testdata`.
- Cost of `fsync`: a first sync of a Flutter sample (32 files) went from about 0.02 s to 0.14 s on macOS, where `File.Sync` is `F_FULLFSYNC`; a sync that changes nothing writes nothing and is unaffected. `go test ./internal/sync` went from about 6 s to 12-18 s.

Known limits:

- A process killed between creating and renaming a temp file leaves a `.<name>.dashcrew-*` file beside the target. It is not read by sync or the catalog; nothing cleans it up yet.
- A new file is `0o644` exactly; `os.WriteFile` applied the umask. Git only records the execute bit, so committed files do not change.
- On Windows, a rename fails while another process holds the target open without delete sharing, where an in-place write might have succeeded. Windows stays unsupported until the v0.7 investigation.

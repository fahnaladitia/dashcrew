# v0.8: commit and push that the agent always confirms

Tier: standard (`internal/profile`, `internal/guard`, `internal/sync`, `core/rules`, docs; generated output of projects that choose it, so new goldens). No golden of an existing sample changes.

## Problem

`policy.agent_commit: true` and `policy.agent_push: true` let the agent commit and push after it asks with its question tool. The question is an instruction: once the policy is on, the guard allows `git commit` whether or not the agent asked. A member who wants the agent to do the git work, but never without their yes, has no setting that holds.

## What the agents can do (documentation read 2026-11-18)

| Agent | Can a PreToolUse hook make the agent ask the user? |
|---|---|
| Claude Code | yes: `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "ask", "permissionDecisionReason": "..."}}` on stdout, exit 0. The reason is shown to the user in the prompt. A `-p` run with no one to answer denies the call. |
| Antigravity | yes: `{"decision": "force_ask", "reason": "..."}` always prompts, ignoring a cached "Always Allow" (`ask` would honour it). |
| Codex | no: `permissionDecision: "ask"` is "parsed but not supported yet"; Codex marks the hook failed and runs the call. So Codex must get a block. |
| Cursor (not supported yet) | `beforeShellExecution` accepts `ask`, effect undocumented; decided with the Cursor adapter. |

Because the guard answers, the prompt also covers what a Claude Code `permissions.ask` rule misses (`bash -c "git commit"`, `env git push`, `git -C . push`): the guard unwraps them first. That is why the guard answers instead of `sync` writing `permissions.ask` rules.

## Knowing the agent for sure

An ask must reach only an agent that honours it: Codex runs a call whose hook answered ask. The guard tells agents apart by the payload today (`agentOf`), and Codex sends `tool_name: "Bash"` like Claude Code, so a Codex shell call reads as Claude Code. The guard answers ask only to an agent it identifies positively, and blocks otherwise:

- Antigravity: its payload shape (`toolCall`), as today.
- Claude Code: an agent argument in its hook command, `"$CLAUDE_PROJECT_DIR/.ai/bin/guard" "$CLAUDE_PROJECT_DIR/.ai/guard.json" claude-code`. The shim passes it on; dashcrew 0.1.0 and newer read only the first argument, so older guards are unaffected. The Codex and Antigravity commands do not change, so Codex needs no new approval in `/hooks`.

This changes `.claude/settings.json` for every project with Claude Code, once, on its next sync (every sample's golden, one line). `doctor` and `check` compare against the new entry; replaceGuardEntry already replaces the old one in place.

## The setting

`policy.agent_commit` and `policy.agent_push` take `ask` besides `true` and `false`:

```yaml
policy:
  agent_commit: ask   # the agent runs git commit; the agent's own prompt asks you each time
  agent_push: ask     # the same for the push of the task branch; needs agent_commit: ask or true
```

- `ask` on Claude Code and Antigravity: a `git commit` (and, with `agent_push: ask`, an allowed `git push`) gets the ask answer, with the reason `[dashcrew guard] git commit needs your approval (policy.agent_commit: ask)`. Everything the guard blocks today stays blocked first: history rewrites, and for push the force, delete, `--all`, `--mirror`, `--tags`, base-branch and unnamed forms.
- `ask` on Codex: the call is blocked with the reason `... Codex hooks cannot ask for approval: run it yourself`, as with `false`. The rules tell the Codex agent to print the command instead.
- When one tool call holds several commands, a block wins over an ask, and an ask over an allow.
- `true` and `false` keep their meaning.

## Rules text

With `ask`, the end-of-task step in `core/rules/git-commit-on.md` becomes: show the commit (files and the message from `dashcrew commit suggest`) and run it; your agent asks you to approve the command, and a refusal means print the command instead. There is no question-tool round before it, so you confirm once, in the prompt that the guard enforces.

## Compatibility

- `.ai/guard.json` gains `ask_git` (a list: `commit`, `push`). A dashcrew older than this release would ignore it and allow the commit without a prompt, so a policy with `ask_git` raises the lock's `guard_min_version` to this release (`version.AskGuardMinimum`), and the shim refuses an older dashcrew, as backend rules and `agent_push` already do.
- A profile with `ask` is refused by an older dashcrew's profile parser (`expected true or false`), which is the right failure.

## Tests first

- `internal/profile`: `ask` accepted for both keys; `agent_push: ask` needs `agent_commit` on; any other string refused.
- `internal/guard`: the policy round trip of `ask_git`; per agent, `git commit`, `bash -c "git commit -m x"` and `env git push origin feat/x` answer ask on Claude Code (JSON, exit 0) and Antigravity (`force_ask`), block on Codex (exit 2); `git push --force` and `git reset` still block; a call with one blocked and one asked command blocks; `Minimum()` is the ask minimum.
- `internal/sync` and conformance: a new sample with `agent_commit: ask, agent_push: ask` for all three agents; its goldens reviewed (rules text, policy, lock minimum).
- `internal/guard` corpus: unchanged for every existing policy.

## Live check before merge

In Claude Code: with `agent_commit: ask`, ask the agent to commit; the prompt shows the guard's reason; deny, then check the agent prints the command; allow, then check it committed. Repeat with an allow rule `Bash(git commit:*)` in `.claude/settings.local.json`, since the documentation does not say whether an allow rule overrides a hook's ask; the result goes in the README.

## Not in this change

- Cursor, which comes with its adapter.
- Asking for other blocked commands (`reset`, `rebase`, formatters): they stay blocked; a profile that wants them asked can come later.

# v0.8: `dashcrew guard init`

Tier: standard (`cmd/dashcrew`, `internal/guard`, `internal/adapters`, `internal/sync`, `internal/doctor`; new CLI output, so new transcripts). No existing golden changes.

Item of the v0.8.0 "Launch-ready" milestone in `docs/ROADMAP.md` and of `docs/ideas/launch-direction.md`: guard hooks and a default policy without a `project.yaml`, as the 10-second way to try dashcrew. Decided 2026-11-18: the hooks are written in the project (committed, the team story), not in the user's home.

Signal to reach: in any git repo, `dashcrew guard init` then an agent's `git push` is blocked, and a later `dashcrew init` + `dashcrew sync` takes the files over without `--force`.

## What it writes

`dashcrew guard init [-p <dir>] [--agents <agent> ...] [--force]`, agents defaulting to `claude-code` as in `init`:

1. `.ai/guard.json`: the default policy, the one a profile with every `policy` default compiles to without a platform's extras: git `commit`, `push`, `stash`, `reset`, `rebase`, `cherry-pick`, `revert`, `merge`, `tag` blocked, formatters blocked, `gh` approvals blocked; no roles (no subagents are written), no vendor imports, no backend rules. One function, `guard.InitPolicy()`, defines it.
2. `.ai/bin/guard`: the shim, `guard.Shim` for the highest `adapters.GuardMinimum` of the chosen agents, executable.
3. Each chosen agent's hook entry, merged as `sync` merges it: `.claude/settings.json`, `.codex/hooks.json`, `.agents/hooks.json` (key `dashcrew-guard`). The user's own entries stay. The three adapters' `Merge` split their hook part into one function per agent, registered in `internal/adapters/registry.go` next to the adapter, so `sync` and `guard init` run the same code and the registry's completeness test covers a new agent.

Nothing else: no AGENTS.md, skills, subagents, MCP, lock or profile.

## What it prints

```
wrote   .ai/guard.json
wrote   .ai/bin/guard
wrote   .claude/settings.json
ok    guard-binary    .ai/bin/guard blocks git push
Commit .ai/ and .claude/settings.json so every clone is guarded. For rules, skills and the rest of the toolkit: dashcrew init, then dashcrew sync.
```

- The `guard-binary` line is the `doctor` probe (dashcrew on PATH, its version, a `git push` event through the shim), shared, not copied. A warn or fail there is printed with its fix, and `guard init` exits 1 on a fail, since the hooks then refuse every tool call.
- Per agent, the step the agent needs before it loads project hooks: Codex, trust the project and approve the hook in `/hooks`; Antigravity, trust the folder.
- A second run writes nothing and says `unchanged` per file.

## Refusals (exit 1)

- `.ai/project.yaml` exists: "this project has a profile; dashcrew sync writes the guard". A synced project's policy comes from its profile.
- `.ai/guard.json` or `.ai/bin/guard` exists and is not what `guard init` writes (edited by hand, or from an older dashcrew): named, replaced only with `--force`.
- An agent dashcrew does not support: the usual `--agents` error, listing `agents.All()`.

## Later `init` and `sync`

- `init` works as today; `.ai/guard.json` does not count as a platform marker.
- `sync` treats a file that is exactly what `guard init` writes (`.ai/guard.json` equal to `InitPolicy`, `.ai/bin/guard` equal to `guard.Shim` of its own `need=` version) as its own, like a file that already holds what it renders: no "Files changed outside dashcrew", no `--force`. Any other unlocked file there is still a conflict.

## `doctor` in a guard-only project

No `.ai/project.yaml` and `.ai/guard.json` equal to `InitPolicy`: `doctor` runs only `guard-policy`, `guard-binary`, `guard-log` and the hook check of each agent whose hook file holds the guard entry, then one `info` line: `guard only (dashcrew guard init); run dashcrew init and dashcrew sync for the toolkit`. Today it prints eight fails there.

## CLI

`isGuardHook` reads every `dashcrew guard <arg>` as a hook with a policy path. `init` joins `install` as a word it does not read that way; a policy file named `init` is passed as `./init`. Hooks never pass that word: they call `.ai/bin/guard` with `.ai/guard.json` or nothing.

## Tests first

- `internal/guard`: `InitPolicy` blocks `git push`, `git commit`, `bash -c "git reset --hard"` and allows `git status`; `WrittenByInit` is true for its own files and false for an edited policy or an edited shim.
- `internal/adapters`: each agent's hook function on an empty folder and on a file with user entries (kept); the registry test fails for an agent without one.
- `internal/sync`: `guard init` files then a profile: `sync` succeeds without `--force` and replaces them; an edited `.ai/guard.json` is still a conflict.
- `internal/doctor`: a guard-only project reports only the guard checks and no fail with a stubbed dashcrew.
- Transcripts: `guard init` in an empty repo, with `--agents codex --agents antigravity`, twice (unchanged), with a profile (refused), an edited policy (refused, then `--force`), then `init -y` + `sync`; `guard --help` lists `init`.

## Docs

README quickstart gains the one-line try (`dashcrew guard init`) before `init`; `docs/commands.md` and `docs/guard.md` describe it; CHANGELOG unreleased.

## Not in this change

- User-level hooks (`~/.claude/settings.json` and the like).
- Cursor: it comes with the Cursor adapter.
- `guard init` options for `agent_commit`, `agent_push` or the formatter: a project that wants them writes a profile.

# v0.7: a release process that catches problems before the tag

Tier: standard (`.github/workflows/ci.yaml`, `.goreleaser.yaml`, a new `docs/release-checklist.md`). No Go code and no generated output change.

Fourth item of the v0.7.0 "Trust" milestone in `docs/ROADMAP.md`.

## What exists

- **`ci.yaml`:**
  - `test` runs vet and test on Ubuntu, macOS and Windows.
  - `gofmt` and `race` run on Ubuntu.
  - `govulncheck` runs on every push and PR, and daily.
- **`release.yaml`:** on any `v*` tag it runs vet, test and govulncheck, then goreleaser v2.18.3, then build provenance (`actions/attest`).
- **`.goreleaser.yaml`:** builds 6 targets, with tar.gz (zip on Windows), `checksums.txt` and a Homebrew formula through `brews`.

## Problems

1. **The release config is exercised only on a real tag.** A broken `.goreleaser.yaml`, a target that stops building, or a `go mod tidy -diff` failure (its `before` hook) shows up after the tag is pushed.
2. **`goreleaser check` cannot be the PR gate.** It exits 2 on the deprecated `brews` block. The block stays on purpose: a formula installs on macOS and Linux, a cask on macOS only (comment in `.goreleaser.yaml`). The roadmap's "move off `brews`" is withdrawn.
3. **A release candidate would ship as a normal release.** `release.yaml` runs on every `v*` tag, and `.goreleaser.yaml` sets neither `release.prerelease` nor the formula's `skip_upload`. Tagging `v0.7.0-rc.1` would therefore:
   - mark it Latest on GitHub;
   - push the rc formula to `fahnaladitia/homebrew-tap`, so `brew upgrade` installs it.

   The roadmap asks for an rc before each minor, so this has to be fixed first.
4. **No upgrade check.** Three minors required a re-sync, and nothing tests that the previous release's output upgrades without `--force`.
5. **No linter beyond `go vet`, and the two fuzz targets never fuzz.** The targets are `FuzzEvaluateShell` (`internal/guard/hardening_test.go:615`) and `FuzzCommands` (`internal/guard/shell/fuzz_test.go:25`). `go test` runs only their seed corpus.
6. **No written checklist.** CHANGELOG 0.2.0 and 0.2.1 list fixes "found in the live run" after the tag.

## Changes

### 1. `release-snapshot` job (PR and main)

The job runs goreleaser with the version pinned in `release.yaml` (v2.18.3): `release --snapshot --clean --skip=publish`. That runs the `before` hook, builds all 6 targets, writes the archives, checksums and formula, and publishes nothing.

- It sets `HOMEBREW_TAP_TOKEN` to a placeholder, because the formula's `token` template reads it. The real secret is never exposed to a PR.
- It then runs the Linux amd64 binary from `dist/` and checks that `--version` prints the snapshot version.

Cost: about 1-2 minutes on Ubuntu.

### 2. Release candidates stay release candidates

In `.goreleaser.yaml`:

- `release: { prerelease: auto }`: a tag with a pre-release part (`-rc.1`) is published as a GitHub pre-release, not Latest.
- `brews[0].skip_upload: auto`: the formula is not pushed for a pre-release, so Homebrew users stay on the last final release.

A plain `v0.7.0` behaves as today. An rc is installed with `go install …@v0.7.0-rc.1` or from the release page.

### 3. `upgrade` job (PR and main)

The previous final release is `git describe --tags --abbrev=0 --exclude='*-*'`, which needs `fetch-depth: 0`. The job installs it with `go install …@<tag>`, so the module version stamps it correctly, and builds the current tree. Then, in a temp git repository with the `sample-other` profile (all three agents):

1. The old binary runs `sync`, and the result is committed.
2. The new binary runs `sync` and must exit 0 without `--force`. A required re-sync is allowed; a conflict is not.
3. The new binary runs `doctor` and must print no `fail` row.

This catches a release whose lock, schema or generated files the next one refuses, the class of break behind "run `dashcrew sync` and commit" in 0.2.0, 0.5.0 and 0.6.0. It does not test a teammate on the old binary against the new output; the compatibility promise in the roadmap covers that at 1.0.

### 4. `staticcheck` job (PR and main)

`go run honnef.co/go/tools/cmd/staticcheck@2026.2.1 ./...`, with Go from `go.mod`. The version is pinned and Dependabot does not see it, so it is bumped by hand, like govulncheck today.

The current findings are unknown. The installed staticcheck 2026.2.1 cannot read the Go 1.27 export data on the maintainer's machine, and CI uses Go 1.26. The first CI run lists them. Each finding is then fixed in the same PR, or a check is turned off in `staticcheck.conf` with a one-line reason. No `//lint:ignore` comments.

### 5. Nightly fuzz (the existing daily schedule)

A `fuzz` job runs only on `schedule`. It runs each target for 3 minutes:

- `go test -run='^$' -fuzz='^FuzzEvaluateShell$' -fuzztime=3m ./internal/guard`
- `go test -run='^$' -fuzz='^FuzzCommands$' -fuzztime=3m ./internal/guard/shell`

On failure it uploads `testdata/fuzz/` as an artifact, so the failing input can be added to the seed corpus with the fix.

### 6. `docs/release-checklist.md`

Steps in order, each one checkable:

1. **CHANGELOG.** "Unreleased" becomes the version. The entries are written from the user's side, with no plan codes. A required re-sync, and any `guard_min_version` bump, is said in the first paragraph.
2. **A minor that changes generated output or the lock** gets `vX.Y.0-rc.1` first.
3. **Live run with the rc** (or `main` for a patch), on one real project per agent:
   - `sync`, then `doctor` with no `fail`;
   - one real session in Claude Code, Codex and Antigravity;
   - in each session, ask the agent to run `git push` and confirm the guard blocks it;
   - upgrade a project synced by the previous release.

   Note what broke. Anything that broke is fixed and goes into a new rc.
4. The rc stays at least 2 days with the office team.
5. **Final tag.** CI green, including `release-snapshot` and `upgrade`, then `vX.Y.Z`.
6. **After release:**
   - `brew upgrade dashcrew` and `go install …@vX.Y.Z` report the version;
   - `gh attestation verify` passes on one archive;
   - the README install lines still work.

## Not in this plan

- **golangci-lint.** It adds a config surface and a second tool to pin; staticcheck covers the checks worth having first.
- **cosign signatures and an SBOM.** Attestation already gives provenance; signing is a separate decision.
- **New install channels** (install script, scoop): v0.8 "Launch-ready".
- **Testing an older Go than `go.mod` names.** `go.mod` sets the minimum, and `go install` users on an older Go get the toolchain download or a clear error.

## Verify

These are workflow changes, so the proof is a CI run on the PR:

- `release-snapshot`, `upgrade` and `staticcheck` pass, or `staticcheck` lists findings to fix in that PR.
- The YAML is checked locally with `actionlint` if it is installed; otherwise the first push shows syntax errors.
- The `upgrade` job is dry-run locally once, with the v0.6.0 binary from `go install` and the current build, before the PR.
- `fuzz` is checked with a manual `workflow_dispatch` run, so the job does not wait a night. This adds `workflow_dispatch` to `ci.yaml`.
- Run locally if goreleaser is installed: `goreleaser release --snapshot --clean --skip=publish`.

## Decisions (maintainer, 2026-11-17)

1. Release candidates stay out of the Homebrew tap (`skip_upload: auto`); the office team installs them with `go install`.
2. Fuzz for 3 minutes per target nightly, to start.
3. The upgrade job was dry-run locally with `go install` of the published releases; goreleaser is proved by the PR's CI run.

## Result

- **`.goreleaser.yaml`:** `release.prerelease: auto` and `brews[0].skip_upload: auto`.
- **`ci.yaml`:**
  - `workflow_dispatch` added;
  - new jobs `staticcheck`, `release-snapshot`, `upgrade` and `fuzz`.
  - The fuzz job prints failing inputs to the log instead of uploading an artifact. The repository pins every action to a SHA, and adding `actions/upload-artifact` needs a pin chosen by the maintainer.
- **`.github/scripts/upgrade-check.sh`:** the upgrade scenario, shared by CI and local runs.
- **Dry runs:**
  - `sample-other` (three agents) synced by v0.6.0, then by v0.5.0, and each time re-synced by the current tree without `--force`. `doctor` showed no `fail` (a `codex-trust` warning and a `me` skip are expected without Codex and a personal profile).
  - Negative case: a build reporting 0.0.1 against a v0.6.0 lock makes the script exit 1 with sync's message.
- **`go build` stamps the version from git** (`0.6.0+dirty` here). The job therefore builds without `-ldflags`, and the build under test is never older than the release it upgrades from.
- **`docs/release-checklist.md`** is written.
- **Not verified locally:** actionlint is not installed and goreleaser is not installed. The YAML parses; the PR's CI run is the proof for the four jobs. The `fuzz` job can be started from the Actions tab (`workflow_dispatch`).

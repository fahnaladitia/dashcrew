# Go as a built-in platform

Tier: large (output layout change: a Go project stops getting `.ai/platforms/go/`; new built-in catalog content; `init` and `platform new` change; new and rewritten goldens).

Open item of `docs/ROADMAP.md` ("Promote Go from starter to a built-in platform"), left out of `docs/plans/v0.8-messages-and-init-plan.md` because it changes the layout of every Go project.

## Why now, and the criterion we are setting aside

P10 (`docs/plans/p10-go-platform-plan.md`) made Go a starter on purpose: `dashcrew platform new go` writes `.ai/platforms/go/` for the team to own, and Go becomes built-in "only later, when a starter that several teams kept unchanged proves generic". That criterion has not been measured: no team has reported on its copy.

What argues for doing it before 1.0 anyway:

- **First five minutes.** `init` on a Go module writes 32 files into the repo that the visitor did not ask for and must commit or delete. A built-in platform writes only `.ai/project.yaml`, as Flutter does.
- **Updates.** A starter copy never changes after it is written: fixes to Go rules (and the backend guard rules) never reach a project. A built-in platform gets them on the next `dashcrew sync`, through the lock's `stale` check, like Flutter.
- **The 1.0 freeze.** The platform list and `platform new` are public surface; deciding after 1.0 would mean a deprecation cycle.

What it costs: the rules become dashcrew's opinion instead of the team's. Teams keep three ways to differ: project packs (`.ai/packs/`), the AGENTS.md project block, and ejecting the whole platform (below).

## Design

### The built-in platform

- `starters/go/` moves to `platforms/go/` unchanged, except `platform.yaml` loses its "Starter from dashcrew {{version}}; edit every file" header. `catalog_embed.go` already embeds `all:platforms`.
- `platform: go` resolves to it; a project platform named `go` still replaces it whole (as a project `flutter` replaces the built-in today), so every existing Go project keeps its exact output until it chooses otherwise.
- The packs `http` (`nethttp`, `chi`, `gin`, `echo`, `fiber`, `none`) and `db` (`pgx`, `sqlc`, `gorm`, `none`) become built-in options, valid in `stack:` and listed in `docs/profile.md`.

### `init` on a Go module

- `go.mod` matches the built-in platform's `detect`, so `init` picks `platform: go` like it picks `flutter`: no starter, no files besides `.ai/project.yaml`. `init --yes` takes it.
- Stack detection: what `starter.GoDefaults` reads from `go.mod` (and `sqlc.yaml`) becomes detection rules in `internal/initproject`, the way `pubspec.yaml` dependencies are read for Flutter, so `init` prints them as evidence (`http [chi]` from `github.com/go-chi/chi/v5`) and asks per family.
- The starter path of `init` (`starterMarkers`, `writeStarter`, the `starter:` line) goes, since Go was its only starter.

### `dashcrew platform new go`, kept as eject

For a team that wants to own its Go rules: it writes the built-in platform into `.ai/platforms/go/` with a header line naming the dashcrew version it came from, and sets `platform: go` as today. The help text says it replaces the built-in from then on and stops receiving its updates. `--http` and `--db` stay. `platform new flutter` works the same way, since it is the same code (decided: every built-in platform can be ejected). `starters/` and `internal/starter` go away; the eject copies from `platforms/`.

### Existing projects

A project with `.ai/platforms/go/` from the starter keeps it: same output, no prompt, no migration. CHANGELOG and `docs/troubleshooting.md` say that deleting an unedited starter folder switches the project to the built-in platform, which gets updates; `dashcrew sync` then rewrites the generated files. (Decided 2026-11-18: no `doctor` line for it, so no frozen hashes of past starters.)

## Tests first

- `internal/catalog`: `go` is a built-in platform with its packs; a project platform `go` still replaces it.
- `internal/profile`: `platform: go` with `stack: { http: chi, db: pgx }` parses without `.ai/platforms/go/`; an unknown `http` option is refused with the list.
- `internal/initproject`: detection from `go.mod` (chi, gin, echo, fiber; pgx, gorm; `sqlc.yaml`), and `init --yes` on a Go module writes only `.ai/project.yaml`.
- `cmd/dashcrew` (`platform new`): the eject writes the built-in platform with the version header and refuses an existing folder, as today.
- Conformance: a new `sample-go-built-in` (`platform: go`, chi and pgx, the three agents). `sample-go` stays as the ejected/project-platform case and must not change.

## Goldens, reviewed before merge

- New: `test/golden/sample-go-built-in/`.
- Changed: transcripts that run `init` on a Go module (`init-a-go-module`, `guard-init`): 32 starter files fewer, the new detection lines. `platform new` transcripts: the header line. The catalog digest in every lock that records it (`sample-release-lines`).
- Unchanged: `sample-go`, `sample-project-platform`, every Flutter and `other` sample, the guard corpus, the frozen `sample-migrate-p3/p3`.

## Docs

`README.md` (built-in platforms: Flutter and Go), `docs/profile.md` (platform table, stack options for Go, the eject), `docs/commands.md` (`init`, `platform new`), `docs/troubleshooting.md`, CHANGELOG, ROADMAP.

## Decisions (2026-11-18)

1. Go ahead without the P10 criterion.
2. No `doctor` line for unedited starters; a CHANGELOG and troubleshooting note.
3. `platform new <name>` ejects any built-in platform (`go`, `flutter`).

## Not in this change

- Rewording the Go rules themselves: they move as they are. Improvements come as normal catalog changes afterwards.
- More Go packs (`grpc`, `ent`, `bun`): good first issues once Go is built in.
- Other starters or platforms.

# v0.8: the guard checks or logs an input it does not recognize

Tier: standard (`guard` and its tests; `corpus_outcomes.txt` may change, and every changed line is reviewed). No generated project file changes.

Item of the v0.8.0 "Launch-ready" milestone in `docs/ROADMAP.md`, under "The guard is the story".

## Why

Three times the guard stopped protecting and nobody noticed: the Codex hook's escaped `$` (55ba40d), the Antigravity hook path (a67453b), and Cursor's input (#46). In the first two the hook never reached the guard. In the third the guard ran and allowed every call, because it did not know the tool name `Shell`, and an unknown tool is allowed without a log line, so `doctor` `guard-log` stayed quiet.

The hook matchers dashcrew writes send only the tools the guard knows:

| Agent | Matcher |
|---|---|
| Claude Code | `Bash\|Write\|Edit\|MultiEdit\|NotebookEdit` |
| Codex | `^(Bash\|apply_patch\|Edit\|Write)$` |
| Antigravity | `run_command` and the write tools of `AntigravityGuardMatcher` |

So an unknown tool name reaching the guard means an agent renamed a tool, another agent runs the hook (Cursor runs Claude Code's), or a matcher was widened. Each is something the user should hear about.

## Today

- `FromHook` (`internal/guard/event.go`) returns `Kind: Other` for a `tool_name` it does not know, or none; `antigravity` does the same for an unknown `toolCall.name`. `Other` is allowed.
- `Event.Malformed` is logged by `Run` to the malformed log, which `doctor` `guard-log` reports ("the guard let N tool calls through unchecked since the last sync"). A reason never quotes the payload.

## Design

1. **A command is checked whatever the tool is called.** An event that would be `Other` but whose input holds a non-empty string command is a shell event:
   - `tool_input.command` (Claude Code and Codex shape, and Cursor's `preToolUse`);
   - a top-level `command` when there is no `tool_name` (`beforeShellExecution`-like);
   - `toolCall.args.CommandLine` for Antigravity.

   An argv list in `command` is read as Codex's is (`shellText`, `argvOf`).
2. **Every such input is logged**, as `unknown tool <name>, checked as a shell command`, or `unknown tool <name>, allowed` when there is no command to check. `<name>` is printed only when it matches `^[A-Za-z0-9_.:-]{1,64}$`; otherwise the line says `a tool name that is not shown`, so the log never carries payload text.
3. **Known tools are untouched**: a `Read`, `Grep` or `WebFetch` that reaches the guard (only through a widened matcher) is still allowed, now with a log line. A write-like unknown tool is not guessed into a write event: a `Read` also has a `file_path`, and calling it a write would block read-only roles from reading.
4. `doctor` `guard-log` wording stays; its detail already reads "logged in <file>", where the reason is.

## Tests (first)

- `internal/guard/unknown_test.go`:
  - an unknown tool with `tool_input.command: "git push"` is blocked, and one with `ls` is allowed; both are logged;
  - no `tool_name`, top-level `command: "git push"`: blocked and logged;
  - Antigravity unknown name with `CommandLine: "git push"`: denied and logged;
  - `Read` with `file_path`: allowed, logged as `unknown tool Read, allowed`, no write rule applied (a `reviewer` role is not blocked);
  - a tool name with spaces or over 64 characters is not printed in the log.
- The corpus runs as is; any changed line in `corpus_outcomes.txt` is a corpus case with a command under an unknown tool, listed in the PR.

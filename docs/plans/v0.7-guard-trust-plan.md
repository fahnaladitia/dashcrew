# v0.7: a guard hook lost in a project's CI, and fail-open causes the guard did not log

Tier: standard (`check`, `doctor`, `guard`; `dashcrew check` output changes, so `cmd/dashcrew` transcripts that print it were rewritten). No generated project file changes.

Second item of the v0.7.0 "Trust" milestone in `docs/ROADMAP.md`.

## How the plan changed

The first draft added a `guard-hooks` doctor check that runs each agent's hook command through `sh`, and a conformance test doing the same for every golden sample, to catch the 55ba40d (Codex `$` escaped) and a67453b (Antigravity working folder) class of bug.

Reading the code before writing it showed `internal/adapters/hook_command_test.go` already does this. It runs the three hook command constants through `sh -c`, each from the folder its agent uses:

- Claude Code from a subfolder, with `CLAUDE_PROJECT_DIR`.
- Codex from a subfolder of a git repository.
- Antigravity from `.agents/`, the root, a subfolder, a monorepo and a checkout without git.
- It also covers the deny fallback when no shim is found.

So a hook command that sync writes wrong already fails CI. A hook that differs from sync's already fails the `hook` checks. A doctor probe would add only environment cases, such as Codex outside a git repository.

The real gap was elsewhere:

- The hook checks run only with `MachineChecks`, so a project's CI (`dashcrew check`) never saw a hook lost to a hand edit of `.claude/settings.json` or a merge. That is the most likely way a team loses its guard.
- Four fail-open causes left no trace until someone ran `doctor`.

Decisions (maintainer, 2026-11-17):

- Drop the probe and the conformance test.
- Move the hook checks into `check`.
- Keep the fail-open log and the blind-spot test.
- `guard-binary` is unchanged.
- The in-session notice moves to v0.9.

## Changes

1. **`doctor.HookChecks`.** It runs `hook`, `codex-hook` and `antigravity-hook` for the profile's agents, reading the committed files only. `antigravity-hook` asks `agy` only with `MachineChecks`. `check.PrCheck.Run` appends these checks after the toolkit checks. `doctor` itself is unchanged.
2. **Fail-open log** (`internal/guard/run.go`). The guard writes a line to the malformed log, with the policy path and never its content, when a policy named by the hook (an argument or `DASHCREW_GUARD_POLICY`):
   - is missing;
   - is not a file;
   - cannot be read or opened;
   - is not valid JSON;
   - is rejected by `LoadPolicy`;
   - cannot be applied (`evaluateAll` error).

   A policy looked for only in the hook's cwd and not found is still allowed silently: that is a folder dashcrew does not manage. Exit codes and output are unchanged, and the corpus outcomes did not move.
3. **`guard-log` wording.** It now reads "let N tool calls through unchecked … with the reasons; update dashcrew if an agent changed its hook format, run dashcrew sync for a broken policy".
4. **`TestDocumentedBlindSpotsAreAllowed`.** It pins the misses the README and SECURITY.md list, plus a control showing that `git push` nested exactly 8 levels deep is still blocked. While writing it, `source /dev/stdin <<EOF … git push … EOF` turned out to be blocked: the guard reads the heredoc. The test therefore uses process substitution (`source <(echo git push)`), which is what the documented miss means.
5. **Docs.** README (doctor table, `check` description, malformed payloads, troubleshooting row) and SECURITY.md say the policy causes are logged and that `check` runs the hook checks.

## Result

- **Tests.**
  - `check`: 2 new (a hook edited away fails the gate; all three agents' hook checks run, without `agy`).
  - `guard`: 2 new (five policy causes logged with their reason; the cwd fallback is not logged) plus the blind-spot test.
  - `doctor`: the `guard-log` test follows the new wording.
- **Transcripts.** 16 `cmd/dashcrew` transcripts gain the hook rows in `dashcrew check` output: 55 `hook`, 24 `codex-hook`, 12 `antigravity-hook`, and 1 `fail hook` in `no-profile`. No other line changed. `test/golden` and `internal/guard/testdata` are unchanged.
- **Found, not fixed.** The status table prints IDs in a 16-column field (`cmd/dashcrew/main.go:339`), and `antigravity-hook` is exactly 16 characters, so it runs into its detail (`antigravity-hookPreToolUse …`). This predates the change: doctor printed it the same way. It is listed with the v0.8 message fixes, because fixing it rewrites every transcript.

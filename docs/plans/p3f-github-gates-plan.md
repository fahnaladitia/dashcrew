# P3f plan: GitHub-enforced gates (MVP)

Tier: large (new commands, a new render target, guard input from gate state, a generated GitHub workflow). Idea and trade-offs: `docs/ideas/github-gates-multi-repo.md`. Multi-repo tasks, the shared toolkit repo, golden diffs on the PR and lessons via PR are later steps, not this plan.

## Goal

The two human gates stop being instructions only:

- **Plan gate.** The agent posts its plan to the task's GitHub issue and stops. A human approves with a `/approve plan` comment, from the browser or the GitHub mobile app. Until then the guard refuses app-code writes on that branch.
- **Merge gate.** `dashcrew check`, a required GitHub check, fails a PR when the toolkit is stale, a required PR section is missing, or the branch's plan issue has no approval.

## What exists

- PR sections: `core/skills/pr-description` (Summary, Changes, Affected files, Testing, Notes / not done) plus pack sections (QA identifiers from `qa`, Analytics from `analytics`). They are prose in a skill, not data.
- `doctor` already checks profile, lock, version, drift and staleness without writing.
- `worktree watch` already reads PR state through `gh`.
- The guard sees each tool call with the hook's `cwd` or workspace path; it does not know the branch.

## Stages

### H1: PR template as data

- New render target `pr_template`: core and pack fragments add their `## <section>` lines. `sync` writes `.github/pull_request_template.md`, so a PR opened on GitHub starts with every required heading.
- An existing template not written by dashcrew is left alone with a warning (like a foreign AGENTS.md); `--adopt` is not offered for it.
- The `pr-description` skill keeps the prose and points at the template for the exact headings.

### H2: `dashcrew gate`

- `dashcrew gate submit plan --file <plan.md> [--issue <n>]`: posts the plan as an issue comment marked `<!-- dashcrew:plan -->` (through `gh`), creating an issue titled after the branch when none is linked. The issue number is kept in `git config branch.<b>.dashcrew-issue`.
- `dashcrew gate status`: reads the issue's comments; the plan is approved when a comment whose first line is `/approve plan` comes after the latest plan comment. It records `{branch: {issue, plan: approved|pending, at}}` in `<git common dir>/dashcrew/gates.json` and prints the state.
- Approvals happen only on GitHub; there is no `dashcrew gate approve`.

### H3: guard

- With `policy.plan_gate: true`, a `write-code` write under `lib/` or `test/` is blocked while the current branch's plan is not approved in `gates.json`. The guard reads the branch from `.git/HEAD` (or the worktree's git dir) without running git, to stay inside the 20 ms budget.
- Always: a shell command that runs `gh` and contains `/approve` is blocked ("approvals are the user's; run dashcrew gate status and stop").
- Branches with no linked issue are not blocked (trivial work keeps its fast path); `dashcrew check` catches them at merge time.

### H4: `dashcrew check`

- Runs locally or in CI; read-only; exit 1 on any failure, one GitHub annotation per failure in CI.
- Checks: `doctor`'s toolkit checks that need no agent or guard binary (profile, project packs, lock, version, drift, stale, guard policy, AGENTS.md size); every heading of the generated PR template present in the PR body (`--pr-body <file>`, or the pull request event in CI); the PR body names its plan issue (`Plan: #<n>`) and that issue has an approval after its latest plan comment.
- In CI it reads GitHub through `GITHUB_TOKEN` (no `gh` needed).

### H5: workflow

- With `ci: { github: true, dashcrew_ref: <sha> }` in the profile, `sync` writes `.github/workflows/dashcrew.yml`: on pull request (opened, edited, synchronize), install Dart, activate dashcrew at `dashcrew_ref`, run `dashcrew check`.
- README: making it a required check in branch protection, and the plan-gate flow.

## Not doing

- A web board, a companion app, a hosted service.
- Telling human from agent on GitHub: both use the same token; the guard prevents mistakes, not malice.
- Re-running the check when an approval arrives after the PR opened (the plan gate normally comes first; a push or an edit re-runs it).
- Golden diffs, lessons via PR, multi-repo tasks, shared toolkit repo: later plans.

## Decisions needed

1. PR headings: fixed English headings from the generated template, with the body in the team's language (proposed, checkable as is), or headings translated per `language.pr`?
2. Plan gate in the guard: opt-in `policy.plan_gate` (proposed, default `false`), or on whenever gates are used?
3. Issue per task: `gate submit` creates one when none is linked (proposed), or it requires an existing issue?
4. Workflow: generated by `sync` when `ci.github` is set (proposed), or only a snippet in the README?
5. Who may approve: anyone whose comment GitHub shows as a repository collaborator (proposed), or a list in the profile (`gates.approvers`)?

## Decisions (confirmed)

1. Fixed English headings from the generated template; the body may be in the team's language.
2. Plan gate in the guard is opt-in: `policy.plan_gate`, default `false`.
3. `gate submit plan` creates an issue when the branch has none linked.
4. `sync` writes the workflow when `ci.github` is set.
5. Any repository collaborator may approve.
